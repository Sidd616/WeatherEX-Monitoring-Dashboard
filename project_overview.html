Probing the platform from the outside

A standalone dashboard that walks the entire surface the WeatherEX product promises its users — nine forecast models, every variable, every forecast day — and reports what is actually reachable right now. It changes nothing in the three repos it watches, and it needs no GCP credentials to do it.

The problem it solves

Why an outside-in prober

The frontend depends on the API server, which depends on the processing pipeline having actually written data into GCS. When a link in that chain breaks, the product does not raise an error — it quietly renders nothing for that one combination. Finding out what is broken today means a person clicking through every model, variable and day by hand.

This dashboard automates that click-through against exactly the surface a real user can select: each model's availableVariables × its forecastDays. Every red square is therefore something a customer could hit right now, which is what makes the board worth acting on rather than just worth reading.

How a check actually travels

Trigger to colored square

Server: four layers, one-way dependencies

Config knows nothing of checks; checks know nothing of HTTP routing

01

Config — declarative truth, zero I/O

server/src/config/models.ts · paths.ts · features.ts

MODEL_CONFIGS holds one entry per model: its cycleHours, availabilityLagHours, whether tile paths are cycle-scoped ({date}_{HH}) or date-scoped ({YYYYMMDD}), whether it writes a _SUCCESS marker, and its tile zoom — 3 for the eight global models, 2 for WFS.

The deliberate omission is the sharpest idea in the file. Per-variable horizon ceilings that sit below a model's advertised range — ICON humidity stopping at 9h, AIFS humidity at 54h, ECMWF's real 144h wall behind a promised 15 days — are not encoded. The checker probes the full promised range and lets a genuine 404 tell the story. A config that already knew the answer would hide precisely the landmines the dashboard exists to find.

paths.ts is pure URL algebra. latestCycle() mirrors the backend's lag logic, fallbackCycle() mirrors its previous-day shift, and four builders dispatch on variable kind: tile, wind-json, ocean-json, daily-tile.

02

Checks — the only place network I/O happens

server/src/checks/http.ts · matrixRunner.ts · featureRunner.ts

http.ts wraps fetch so it never throws — timeouts and transport errors land in a field instead — and adds a hand-rolled semaphore in about fifteen lines, no dependency. Tier 1 walks the model grid; Tier 2 checks the features that are not day-shaped at all.

Tier 2 reads the JSON body, not just the status line. That is forced by a real property of the platform: /public/point and its siblings swallow a missing array into 200 success:true value:null. A status-only checker would report confident green over an outage.

03

Storage — four tables, one writer

server/src/db/db.ts

Built-in node:sqlite, so there are no native modules to compile and no service to run. cells, features and markers are upsert-on-conflict, holding the latest result per key; runs is the one append-only table. No SQL exists outside this file — everything above it calls typed functions.

04

Orchestration — cron in-process, one guard

server/src/scheduler.ts · routes/index.ts · index.ts

node-cron runs the matrix sweep every 30 minutes and the feature sweep every 10, both behind a single runInProgress boolean: whichever arrives first wins, the rest log and return. POST /api/run and the startup pass are the only paths that run both tiers together. Triggers return immediately rather than blocking on the sweep, so the Run-now button never holds a request open.

The status algorithm

What it takes to earn each color

The four states are deliberately asymmetric. Green is cheap, red is expensive: only two independent, cleanly-resolved 404s can produce it. Anything the checker could not read conclusively becomes gray, which means this check failed, never this feature is broken — confusing the two is how monitoring tools train people to ignore them.

Tier 1 cell resolution, in order
Probe outcomeResultReasoning
primary 200 green Serving normally. No fallback request is made at all.
primary clean 404
→ fallback 200		 yellow Today's cycle is missing, but the previous day at fh+24 answers — the exact shift the backend performs itself. The user sees data; it is just older than advertised.
primary clean 404
→ fallback clean 404		 red The only branch permitted to claim confirmed breakage. Both probes had to cleanly resolve to not-found, not merely fail to resolve.
403 / 500 / timeout
on either probe		 gray Inconclusive. An unreadable check is never downgraded to red just because it happened on the second probe rather than the first.

Tier 2 adds a payload rule

Features resolve against the public API instead of GCS: a 503 is red outright (the backend's never-loaded case), any other non-2xx is red, a 2xx with an unparseable body is gray, success:false in the body is red regardless of status, and a truthy stale or obsStale flag is yellow. Loaded-but-old is a genuinely different failure from missing, and the board keeps them apart.

Never trust the clock

The hardest-won piece of logic in the repo

resolveConfirmedCycle() — why a lag estimate is not good enough

The obvious implementation picks the cycle that should be ready by now and probes it. That implementation was tried, and it failed in production for a structural reason: the fallback path derives from the same estimate. One optimistic guess therefore misses both probes, and an entire model reds out while a complete, very recent cycle sits one step behind it.

So the checker resolves cycles the way the real backend does — it only ever probes a cycle whose _SUCCESS marker it has actually seen, walking newest-first up to seven days back, per variable.

  • The 17-minute miss. An AIFS estimate landed just past its configured 8-hour lag on a cycle whose marker did not exist yet, while the previous cycle was fully live.
  • Why per-variable, not per-model. AIFS rain_accumulation had a marker for a cycle that temperature did not. Resolving once per model and reusing it would mis-cycle every variable that finished at a different time.
  • Why seven days, not one. An et0 check found neither today's nor yesterday's cycle complete, but one from two days back — which was the exact cycle the live frontend was serving tiles from. A one-day lookback would have reported the whole variable broken while users were looking at its data.
  • Why bounded at all. Past roughly a week, "still findable if you search far enough" stops being meaningfully different from broken. Searching indefinitely would paper over exactly what the board is for.

Frontend

No router, no state library, no data-fetching library

App.tsx owns all state. It loads all nine model details up front — cheap at that size, and having them in hand is what lets search and sort work across variable names rather than just model labels — then polls summary and run-status every 20 seconds.

The refresh trick is worth copying: heavy refetches fire only when lastRunAt actually moves, because nothing else can change between runs. A 20-second poll therefore costs two small requests, not a full reload of the board.

Logic lives in pure modules so components stay presentational. status.ts handles severity tallying — note newRed, which counts reds only on rows without a knownGap, so documented landmines never drown out fresh breakage. grid.ts expands sparse cells into dense day rows, keeping never scheduled (rendered blank) visually distinct from checked, unknown (rendered gray).

One Tailwind 4 gotcha

Status class names are spelled out as complete literals in status.ts rather than composed. Tailwind's scanner reads source text, so a template literal like text-status-${x} is invisible to it and the class is never generated.

Loose ends in the code

  • TILE_PUBLIC_BASE is documented in .env.example, but paths.ts hardcodes it. Setting the variable does nothing.
  • The Dockerfile copies web/dist into the image, but index.ts never calls express.static. A container built today would serve the API with no UI.
  • getOverallCounts() sums the cells table only, so a features-only cron run writes matrix counts into its own runs row.
  • checkDailyTileCell resolves to result.ok ? green : red, so a timeout on an et0 or gdd cell reports confirmed-broken. Every other cell path would call that gray — this is the one place the four-state discipline is not applied.
